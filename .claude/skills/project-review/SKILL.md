# Project review

Runs every Friday. The last Friday of the month is the **monthly** review (weekly + refinement);
every other Friday is the **weekly** review.

Active projects are `projects/active/*.md`, background ones `projects/ongoing/`, stuck ones `projects/blocked/` (with `blocked:` and `blocked_by:` in frontmatter); drafted projects waiting to start are in `projects/ready/`, ideas not yet started in `projects/proposed/`. Project files
are the maintainer's own documents and vary in shape, from a one-line idea to the fuller template
in `projects/README.md`. Respect their wording; suggest structure rather than imposing it.

## First: pick up decisions

The maintainer answers hq issues by commenting on them. Act on those answers before reviewing
projects, since they often move one. Most weeks there are few.

1. List open issues in `<org>/hq-private` assigned to the maintainer:
   `gh api "repos/<org>/hq-private/issues?state=open&assignee=<maintainer>&per_page=100"`.
2. For each one, read the comments (`gh api repos/<org>/hq-private/issues/<n>/comments`).
   A comment needs acting on when it was written by the maintainer's account, and no comment by an
   agent after it says `<!-- hq:followup -->`. Agents post as the maintainer too, so tell them apart
   by that marker and by the `_Generated by Claude Code_` footer: a comment from the maintainer's
   account without the footer is the maintainer's.
3. Also act on checklist items the maintainer has ticked or edited in the body when the issue
   says ticking is the approval.
4. Look for branches without PRs, each one should either be a known working branch, e.g. 'badges', or an experimental branch that should be challenged if not active for more than 4 weeks. Otherwise refresh the branch from main, and raise a PR if clean or raise an Issue if there's doubt about automatically removing. If the maintainer has already commented on the branch, follow their instructions. If not, ask in a comment whether to delete or keep it.

For each decision, in the persona that owns the issue's label (see `team.md`):

- **Approval or clear choice:** carry it out within the rules in `AGENTS.md`. Changes to product
  repos are PRs, one repo and one theme each, review requested from the maintainer. Where an open agent
  PR already covers that theme in that repo, push to its branch instead of opening a new one.
  Policy wording the decision settles goes into `policies/` in `hq` in the same run.
- **Unclear or conflicting answer:** don't guess. Post a short question with
  `<!-- hq:needs-action -->` so it pings.
- **Too big for one run:** do what fits, list the rest in the follow-up comment, and leave those
  items unticked.

Then post one follow-up comment per issue. It starts with `<!-- hq:followup -->`, lists what was
done (PR links, commits) and what's left, and ticks the items now done in the body. Add
`<!-- hq:needs-action -->` only if it asks for something new. Close the issue when every item is
done or handed to a PR the maintainer only has to merge.

## Then: chase stale handoffs

Handoffs (**For other roles** in a report, see `team.md`) are picked up only when the persona they
name next runs, and some personas run rarely (tech-writer's only process is quarterly). Make sure
none just waits.

1. Read the **For other roles** sections of reports in `hq-private/reports/` written in the last
   six weeks.
2. An item is **picked up** when a later report by the named persona lists it under its handoffs
   picked up, or the fix is evident (the file, setting or snapshot now shows it done). An item marked
   resolved in the report itself is done.
3. File an hq issue for an item that is not picked up, is more than 7 days old, and whose persona has
   no scheduled run (per **Who:** and **When:** in `processes/`) in the next 14 days. One issue per
   item, labelled for the persona's area, its body linking the report section and starting with
   `<!-- hq:handoff <report path> <persona> -->`. Search open and closed issues for that marker
   first and don't file twice. Items that are pm's own are worked here, not filed.
4. An item carried forward as "still open" in two or more reports gets an issue regardless of the
   persona's schedule.

## Weekly, per blocked project

- Has the block cleared? Check what `blocked_by:` names: the project it waits on is done, the issue closed,
  the PR merged. If so, propose moving it back to `projects/active/` (or `ready/`) in the project's hq issue.
- Is `blocked:` still the real reason? If it waits on the maintainer, say so plainly and make sure an hq issue
  asks for exactly that.
- Blocked for more than 6 weeks (the site shows **Blocked since**): challenge it. Is there a way round the block,
  a smaller part that can go ahead, or is it better shelved? Put the question in the project's hq issue.

## Weekly, per active project

- What moved this week: ticked tasks, Log entries, related commits/issues/PRs in the product repos
  (`gh search issues/prs --owner <org> --updated >=<date>`), relevant process reports
  (e.g. an alignment proposal that belongs to a project).
- Status check: is its folder still true? Blocked, and on whom (propose `projects/blocked/` with the reason)?
- Challenge progress: an active project with no dated Log entry or commit in 3+ weeks (the site's **Last
  work**) is stalled. Say what would get it moving, or propose `ongoing/` (it's really background work),
  `blocked/` or `shelved/`. Ongoing projects aren't expected to move weekly: check them monthly, for whether
  they're still worth carrying.
- **Next steps**: the 1–3 concrete next tasks, each tagged `@agent` / `@pair` / `@human`. For
  `@agent` tasks, say whether you could do them next run unattended.

Apply clear factual updates directly (tick tasks evidenced as done, add a dated Log entry). The
project tables are generated from each file's folder and `summary:`, so there's no index to edit:
moving a file between folders is the whole change. Add a `summary:` to any project missing one
(`mise run check-hq` lists them). Leave goal/scope/priority changes as proposals.

## Monthly, additionally

- **Refine the project itself**: is the goal clear and testable? Is it the right size, or should
  it split/merge? Do "Soon"/"Distant" items now have the feedback they were waiting on (check
  process reports)? Still worth doing?
- For a free-form project that has grown many steps or approval gates, propose the fuller shape
  (Goal / Context / Plan with tagged tasks / Decisions / Log) as a draft in the report; leave
  short projects short.
- Cross-project: dependencies, conflicts, and what should be next to start given capacity.
- Ideas raised in process reports that deserve to become projects (draft them for `projects/proposed/`).
- Is it really a policy? A standing rule with no end state (a preferred library, a docs toolchain,
  "all HA components have no YAML") belongs in `policies/` (see `policies/README.md`), with any big
  catch-up work kept as a project. Propose the move and a draft of the policy.
- Proposed projects: is any now drafted enough to be ready (move to `projects/ready/`), or better shelved?
- Ready projects that should start given capacity (propose moving to `projects/active/`); active projects that look finished (propose moving to `projects/done/`) or abandoned (propose
  `projects/shelved/` with a dated reason). Moves between folders are the maintainer's call.
- Shelved projects: has anything changed (platform, demand) that makes one worth reviving?

## Output

`hq-private/reports/projects/YYYY-MM-DD.md`: a **Decisions picked up** line per hq issue acted on
(issue link and what was done, or "none"; the detail is in the follow-up comment, since the report
is public), a **Handoffs chased** line (issue links filed this run, or "none"; no item detail, since
handoffs can come from private reports), one section per project (status, moved, next steps, flags), then for the monthly review
a **Refinements** section with proposed edits as diffs or drafts.

Every `@human` next step, flag (blocked on the maintainer, stalled) and refinement needing a decision
must be in an hq issue (label `project` + area, one per project, per "Issues and PRs" in
`AGENTS.md`) linking back to its section here; update the project's existing issue rather than
opening another.
