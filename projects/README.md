# Projects

What's in progress, ongoing, blocked, ready to start, proposed, finished or shelved. On the site, the [list of projects](./) is generated by the build
from each project file: its folder gives the group, its `title:` (or first heading) the name, and its `summary:` the goal.
Nobody edits it by hand; on GitHub, browse the folders instead.

## Project files

One markdown file per project.

The folder is the status; moving the file is the whole change of status.

- `projects/active/*.md` — in progress, as a concerted effort.
- `projects/ongoing/*.md` — background or opportunistic work, done as products are touched rather than in one
  push (e.g. a migration applied to each repo as it's next released). No end date expected soon.
- `projects/blocked/*.md` — started, but can't move until something else happens. Needs `blocked:` in
  frontmatter saying why, and optionally `blocked_by:` naming what it waits on: another project's file name,
  a path in hq, an issue or PR (`hq-seed#3`, `owner/repo#12`) or a URL. Move it back when the block clears.
- `projects/ready/*.md` — drafted and ready to start, waiting for capacity.
- `projects/proposed/*.md` — ideas not started yet, either a bare idea, or a draft being worked up.
- `projects/done/*.md` — finished projects.
- `projects/shelved/*.md` — rejected or postponed indefinitely. Add a dated line saying why.

On the site, the list shows the dates that fit each status: when a project was proposed, became ready,
started (`started:` in frontmatter, else when it first went into `active/` or `ongoing/`), was last worked on
(the latest dated **Log** entry, or the last commit to a project with no Log), was blocked, completed or shelved. They come from git history, so
there's nothing to keep up to date by hand. Done and shelved projects are folded away.

A project file starts as a title, a one-line `summary:` in its frontmatter (the goal in the tables) and a
one-paragraph goal; add sections as the project needs them
(e.g. Done / Remaining, or Now / Soon / Distant). Larger projects with many steps or approval
gates can use the fuller shape, as `aws-migration.md` does:

```markdown
---
title: Short name
summary: One line: the goal, as shown in the project tables
lead: infra-lead | pm | marketing | architect   # persona that drives it
owner: <maintainer>
started: YYYY-MM-DD
productline: applies across 1 or more product lines
programme: <slug of the owning project>   # optional, see Programmes below
blocked: <why it can't move>               # in projects/blocked/ only, required there
blocked_by: <what it waits on>             # optional: a project, issue (repo#12) or URL
---

## Goal / ## Context / ## Plan (tagged tasks) / ## Decisions / ## Log
```

## Programmes

Bigger programmes of work span several projects. Each project in one says so with `programme:` in its
frontmatter, naming the project that owns the programme by its file name without `.md` (e.g.
`programme: env-separation`). The owning project is an ordinary project file, in whatever folder fits its own
status; its members stay in theirs, since they're often at different stages.

On the site, each project's programme is shown beside it, and a Programmes section lists each programme with all
its projects and their status. `mise run check-hq` checks that every `programme:` names an existing project.

Considered and dropped: a directory per programme. Its projects are rarely all at the same status, so one
folder can't say where each stands.

Tasks are checkboxes tagged with who executes them:

- `@agent` — an agent can do it unattended (read-only, or reversible and inside this repo)
- `@pair` — agent does the work, human reviews/approves before it takes effect
- `@human` — needs the human (console logins, payments, credentials, judgement calls)

`- [ ] @pair Write Terraform for the Route53 zones` · `- [x] @human Create AWS account (2026-10)`

When a task becomes real work, link it: an `@human` task gets an hq issue (labels `project` + area),
a `@pair` task gets the PR the agent built. See "Issues and PRs" in `AGENTS.md`.

Rules for agents working a project: work the first unblocked task you're allowed to; never cross a
`@pair` gate without recorded approval in **Decisions**; add a **Log** entry each session; if
blocked, say on what (in frontmatter `status` if the file has it, otherwise in the Log).
